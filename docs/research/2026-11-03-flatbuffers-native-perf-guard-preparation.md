## Executed guard counterexamples

The first22 unit guards produced21passes and one failure: an inherited sampler
acknowledgement endpoint was not refused. Actual Darwin pipe metadata shows
different identities for read/write endpoints. The fix declares both actual
creator endpoints and their access directions rather than inferring a peer
identity. All24 guards then passed. This is not Linux inheritance evidence.

Source review identified a missing release-channel binding. A new actual test
confirmed that a wrong release pipe was accepted. The correction binds a
distinct go channel and its writable endpoint, rejecting wrong pipes, read
ends, reused numeric descriptors and aliases to sampler channels before token
writes. All28 guards pass at the final prototype hashes in the root assessment.

The guards also cover ordering, spoofed workload-stdout acknowledgement,
process-instance/image changes, unchanged argv/environment/credentials,
exclusive consumed markers, symlinks, short writes, injected ENOSPC, partial
token failure and refusal to retry. Disk faults and PID reuse are synthetic;
the real disk was not filled and the host was not forced to recycle PIDs.

The first wrong-channel test launch was refused by the official exclusive
resource lease before its archive/test block. That refusal is retained. The
actual before-failing test ran only after the lease became available. No other
workload reservation was bypassed. Every source version and failure log remains.

## Pending controller and capability proof

Keep the blocked launcher/driver at the original unprivileged UID/GID and
environment. A privileged sampler must attach to that PID with inheritance;
running the driver as a `sudo perf` child would change credentials/environment.
Sampler stdin/stdout control/ack pipes must be distinct from workload streams,
even when their descriptor numbers are both0/1 in different processes. Do not
mistake a sudo launcher PID for the actual recording owner.

Upstream perf documentation describes process attachment, inheritance controls,
disabled startup and acknowledged control commands. This is design context,
not proof of the future host's perf version, permissions or kernel behavior.
[Upstream v6.8 perf-record documentation](https://github.com/torvalds/linux/blob/v6.8/tools/perf/Documentation/perf-record.txt).
A bounded real kernel capability control over owned non-benchmark processes
must still establish the actual inheritance/arming behavior before data.

The current module only guards supplied witnesses and pipe writes. It does not
implement blocked-exec consumption, a real controller, privileged sampler
identity discovery, process/image/lineage collection, a kernel capability probe
or capture orchestration. It has no benchmark/capture entrypoint. Those pieces,
their meaningful tests and own verification/provenance/declaration/root review
remain the next work. No profiling/heap RPC, sample reset, setFlag, JIT-symbol,
AOT, SDK, GC, allocator or worker-policy change is a workaround.

Full verification has not started. Last observed free space was7.60GB, below
the12GiB full-build preparation floor; the controller is also incomplete.
No new cleanup occurred. Focused guard tests used the official exclusive lease
and a separate1GiB small-test floor. No source/native mutation occurred during
their execution.

All original strict results remain failed and retained. Whole-execution native
samples would include startup, warmups, observers and cleanup; they cannot prove
gate-interior CPU parity, allocation volume, managed stacks, physical RSS or
causal repair. There is no new performance result or production fix yet.
